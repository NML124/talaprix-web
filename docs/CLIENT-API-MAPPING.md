# Préparation du branchement Supabase

Inventaire issu des sources Flutter et des Edge Functions locales, sans appel de mutation ni déploiement. La base mobile est SUPABASE_URL + /functions/v1. Le web devra réutiliser sa configuration d'environnement et les mêmes contrats ; aucune clé ni URL de VPS ne doit être inscrite dans les composants. Les droits JWT doivent rester vérifiés côté serveur. Cette phase n'implémente aucun endpoint.

La connexion utilisera le SDK Supabase (signInWithOtp, verifyOTP email, Google). Vérifier les origines, redirections web et la longueur réelle des OTP avant de brancher les six cases du design. La simulation locale ne valide aucune identité.

## Écarts à organiser après validation des interfaces

1. **Variantes et état dans l'optimisation.** Le contrat actuel choisit à partir de product_id. Il faut conserver offer_reference_id et l'état sélectionné pour éviter de remplacer un 128 Go neuf par un 256 Go reconditionné. Étendre le contrat avec des champs optionnels compatibles mobile, ou versionner après accord.
2. **Coordonnées et filtres boutiques.** get-offer-reference-offers ne fournit pas le téléphone et retourne shop_image null. get-shops-list n'expose pas explicitement téléphone, catégories ou commune. Prévoir un enrichissement public cohérent avant les boutons WhatsApp et les filtres de carte. Ne pas déduire un numéro depuis un nom.
3. **Favoris/alertes produit ou référence.** Décider l'intention commune mobile/web. Les endpoints actuels travaillent au niveau produit ; ne pas leur envoyer un UUID de référence comme product_id. Ajouter mise à jour/suppression d'alerte si les interrupteurs doivent modifier une règle existante.
4. **Baisse de prix de la semaine.** get-pub est de la publicité, pas un historique de prix. Il faut un agrégat fiable sur les prix observés, ou retirer ce bloc lors du branchement si ces données manquent.
5. **Formulaire commerçant.** La maquette demande commune, WhatsApp, catégories et consentement, sans session ni coordonnées GPS. Cela ne correspond pas à request-become-shop. Choisir une collecte de prospects adaptée ou un parcours authentifié avec adresse/position ; ne pas créer directement une boutique publique depuis ce formulaire.
6. **Panier multiappareil.** À prévoir uniquement si requis : lecture/mise à jour d'un panier utilisateur et gestion des références/quantités. post-selection seul n'établit pas ce contrat.
7. **Slugs et provenance.** Utiliser un identifiant stable de référence dans les routes et définir le slug lisible. Vérifier les champs source et date d'observation avant d'afficher une fraîcheur de prix. Ne pas inventer stock, provenance ou dates.

Le client HTTP web devra conserver apikey et Authorization selon le contrat des fonctions, avec JWT utilisateur pour les routes privées. Aucun service role dans le navigateur. Le taux de démonstration 1 USD = 2265 CDF ne doit pas devenir une valeur de production. Les fonctions historiques get-detail-product/search-products-nearby peuvent aider à comprendre l'existant ; le catalogue moderne doit rester centré sur les références pour comparer les bonnes variantes.
